# Contributing to OpenCommons

OpenCommons is a distributed, meaning-indexed concept commons: verified scientific and algorithmic knowledge that any agent or human can query and extend. Published research: [DOI 10.5281/zenodo.23391160](https://doi.org/10.5281/zenodo.23391160).

There are two ways to contribute, and the first one needs no pull request at all.

## Path 1 — Contribute knowledge (no pull request)

A concept is a small, pure, self-contained Python function that does one thing and provably does it correctly: a numerical primitive, a hashing trick, a statistical routine, a systems invariant.

The bar for entry:

1. **Source code** — a complete, typed, dependency-light function.
2. **One-line summary** — what it computes.
3. **At least 3 concrete examples** — real inputs and outputs.
4. **At least 1 executable invariant** — a boolean property that must hold for all valid inputs.

If a candidate cannot meet this bar, it does not go in. That is the whole review system, and it is enforced mechanically.

### Submit via CLI

```bash
pip install -e .
opencommons record --help   # or use the interactive /commons flow in kardashev-cli
```

### Submit via MCP (from any coding agent)

Attach `opencommons-mcp` (`kardashev integrate all`) and ask your agent to record a verified function. Agents running through `kardashev-cli --with-opencommons` do this automatically as a side effect of real work.

### What happens on submission

Your function passes through a 5-gate adversarial review: AST safety sandbox (no imports of untrusted code, no dunder escapes, no `eval`/`exec`), static capability filtering, 16-probe behavioral fingerprinting, contract-example verification, and equivalence-class deduplication. Passing blocks are committed to the CRDT store and gossip-synced to the hub. Failing or ambiguous blocks are quarantined — never silently merged, never lost.

If you discover a counterexample for an already-verified block in production, report it via the counterexample ratchet (`record` with `failing_block_id` and `counterexample_args`); this quarantines the flawed block network-wide and is itself a valued contribution.

## Path 2 — Contribute code

The engine itself: retrieval, fingerprinting, peer review gates, CRDT sync, MCP server, experiments.

### Setup

```bash
git clone https://github.com/kardashevproject/opencommons.git
cd opencommons
python -m venv .venv
.venv/bin/pip install -e ".[dev]"
```

### Before you open a pull request

```bash
PYTHONPATH=src pytest -v
PYTHONPATH=src python3 experiments/r001_ingestion_and_equivalence.py   # spot-check the benchmark you touched
```

### Guidelines

- **Keep changes focused.** One fix or feature per pull request, with a test that fails without it.
- **Claims must be true.** Benchmarks, docstrings, and paper claims must be reproducible from this repo. If a number can't be regenerated by a command in this README, it doesn't get written.
- **No personal or machine identifiers.** No home-directory paths, usernames, hostnames, or keys — including in tests, fixtures, and examples. Use `~` or placeholders.
- **Style.** Match the surrounding code; type hints on public functions.

## Review SLA

- Knowledge submissions: verified asynchronously by the automated 5-gate pipeline, typically within minutes; edge cases land in the human review queue (`opencommons review`).
- Pull requests: first response within about a week; anything blocking a release is prioritized.

## Commit messages

Conventional prefixes (`fix:`, `feat:`, `docs:`, `test:`, `refactor:`, `chore:`), optional scope, plain factual summary.
